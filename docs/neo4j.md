# How TraceReason uses Neo4j

Neo4j stores authenticated users' project memory as a graph. Records describe technical decisions, components, dependencies, bugs, fixes, reasons, and evidence. Relationships make the reasoning between records explicit: which component a decision affected, which dependency a bug involved, and which evidence supports a fix.

The interactive browser graph renders this stored snapshot through React Flow. Gemini receives a bounded subset of that snapshot to explain a possible connection. A graph connection supplies context; it does not prove that one event caused another.

The separate local demo uses browser storage and never accesses Neo4j. An authenticated **Create sample project** action writes a new synthetic project to Neo4j instead.

## Node labels and stored properties

TraceReason uses namespace labels so its constraints and queries target its own nodes within an existing database.

| Label | Properties |
| --- | --- |
| `TraceReasonUser` | `firebaseUid`, derived from a verified Firebase token |
| `TraceReasonProject` | `id`, `name`, `description`, `createdAt`, `updatedAt`; synthetic samples also have `synthetic` |
| `TraceReasonRecord` plus a domain label | `id`, `projectId`, `kind`, `updatedAt`, and the domain fields below |

Each record has two labels, for example `:TraceReasonRecord:Decision`. Every record, including a Reason, carries `projectId`. The API represents domain fields inside a `fields` object; the repository stores those fields as flat Neo4j node properties and reconstructs the API object on reads.

| Domain label | Domain fields |
| --- | --- |
| `Component` | `name`, `description` |
| `Dependency` | `name`, `version`, `description` |
| `Decision` | `title`, `description`, `decidedAt`, `alternatives`, `revisitConditions`, `status` |
| `Reason` | `text` |
| `Bug` | `title`, `symptoms`, `errorMessage`, `status`, `occurredAt` |
| `Fix` | `title`, `description`, `appliedAt`, `verificationNotes`, `verificationStatus` |
| `Evidence` | `type`, `title`, `url`, `excerpt`, `createdAt` |

IDs are strings generated by the server. Metadata timestamps use ISO strings; record date fields use validated `YYYY-MM-DD` strings. See [model.ts](../src/lib/model.ts) for allowed status values and length limits.

## Relationship model

Ownership and project membership are created by the repository:

```text
TraceReasonUser -[:OWNS]-> TraceReasonProject
TraceReasonProject -[:HAS_COMPONENT]-> Component
TraceReasonProject -[:HAS_DEPENDENCY]-> Dependency
TraceReasonProject -[:HAS_DECISION]-> Decision
TraceReasonProject -[:HAS_REASON]-> Reason
TraceReasonProject -[:HAS_BUG]-> Bug
TraceReasonProject -[:HAS_FIX]-> Fix
TraceReasonProject -[:HAS_EVIDENCE]-> Evidence
```

Users can create these domain connections through the relationship form:

| Relationship | Source | Target |
| --- | --- | --- |
| `DEPENDS_ON` | Component | Dependency |
| `AFFECTS` | Decision or Bug | Component |
| `HAS_REASON` | Decision | Reason |
| `INVOLVES` | Bug | Dependency |
| `RESOLVED_BY` | Bug | Fix |
| `MODIFIES` | Fix | Component |
| `SUPPORTED_BY` | Decision, Bug, or Fix | Evidence |
| `SUPERSEDES` | Decision | Decision |

Domain relationships carry an `id` and `projectId`. Ownership and membership edges are structural and are not included in the record graph returned to React Flow. `HAS_REASON` has two uses: project membership and the explanation of a decision; the source node distinguishes them.

Relationship creation checks ownership, loads both endpoints within that project, rejects self-links and incompatible types, and checks the relationship count. `MERGE` reuses an existing relationship with the same source, target, type, and project rather than creating a duplicate.

## Constraints and indexes

Run `npm run db:setup` to apply these statements. They use `IF NOT EXISTS`; setup preserves records and can be repeated.

```cypher
CREATE CONSTRAINT tracereason_user_uid IF NOT EXISTS
FOR (n:TraceReasonUser) REQUIRE n.firebaseUid IS UNIQUE;

CREATE CONSTRAINT tracereason_project_id IF NOT EXISTS
FOR (n:TraceReasonProject) REQUIRE n.id IS UNIQUE;

CREATE CONSTRAINT tracereason_record_id IF NOT EXISTS
FOR (n:TraceReasonRecord) REQUIRE n.id IS UNIQUE;

CREATE INDEX tracereason_record_project IF NOT EXISTS
FOR (n:TraceReasonRecord) ON (n.projectId);

CREATE INDEX tracereason_record_kind IF NOT EXISTS
FOR (n:TraceReasonRecord) ON (n.projectId, n.kind);
```

There is no embedding index or full-text index in this MVP. Search and bounded traversal operate in TypeScript on the selected project's snapshot. The database constraints enforce unique node identities; ownership and endpoint compatibility are application checks.

## Driver and transaction lifecycle

The server creates one reusable `neo4j-driver` instance from `NEO4J_URI`, `NEO4J_USERNAME`, and `NEO4J_PASSWORD`. Each repository operation opens a session for `NEO4J_DATABASE`, which defaults to `neo4j`, executes a managed read or write transaction, and closes the session in `finally`.

Connection, acquisition, and transaction retry settings are 10 seconds. The database command script closes its driver when finished. Multi-step writes such as sample seeding execute in one managed transaction, so a failed transaction does not leave a partially seeded project.

Values are passed as Cypher parameters. Interpolated labels and relationship types come from the validated, closed domain allowlists; user text and model output cannot become executable Cypher.

## Ownership-scoped query examples

The API verifies a Firebase ID token before calling the repository. `$uid` below means that verified UID, never a trusted value from the request body. `$projectId` identifies the requested project but does not grant access.

An ownership check uses this pattern:

```cypher
MATCH (u:TraceReasonUser {firebaseUid: $uid})
      -[:OWNS]->(p:TraceReasonProject {id: $projectId})
RETURN p.id AS id
```

The record snapshot query uses the same ownership path:

```cypher
MATCH (u:TraceReasonUser {firebaseUid: $uid})
      -[:OWNS]->(p:TraceReasonProject {id: $projectId})
MATCH (r:TraceReasonRecord {projectId: p.id})
RETURN properties(r) AS r
ORDER BY r.updatedAt DESC
LIMIT 501
```

The extra result detects projects exceeding the 500-record limit; the server returns an error instead of silently omitting data. Relationships are read only when both endpoints and the edge belong to the selected project, with the same extra-result check for the 2,000-relationship limit.

For manual read-only inspection in Neo4j Browser, supply your own parameters and retain the ownership scope:

```cypher
MATCH (:TraceReasonUser {firebaseUid: $uid})
      -[:OWNS]->(p:TraceReasonProject {id: $projectId})
MATCH (d:TraceReasonRecord:Decision {projectId: p.id})
      -[:HAS_REASON]->(r:TraceReasonRecord:Reason {projectId: p.id})
RETURN d.title AS decision, r.text AS reason
LIMIT 20
```

These snippets illustrate repository behavior; application access should go through authenticated API endpoints. A person with direct database credentials has database-level access outside the application's ownership checks.

## Persistence, deletion, and limits

Authenticated writes survive page reloads because they are saved in Neo4j. Updating a record replaces its validated properties while retaining its ID and kind. Deleting a record removes its incident relationships. Deleting a project removes its own TraceReason records and the project node, leaving the user node and other projects intact.

The current limits are 100 projects returned by the project list, 500 records per project, and 2,000 domain relationships per project. Snapshot reads reject oversized projects. The UI requires confirmation for destructive actions; the API itself does not provide undo or soft deletion.

Graph node positions are currently presentation state, not Neo4j properties. Dragging changes the current graph layout; it does not update the stored record or persist that position across reloads.
